    01 ตัวแปรกับค่า

    ตรรกะถูกทั้งหมดแต่ยังได้ 0 คะแนน มักเกิดจากพื้นฐานในบทนี้

    บทที่ 01~18 นาทีเริ่มต้น

    จบบทนี้ต้องทำได้

    • อธิบายว่า const ล็อกอะไร และทำไมยังแก้ property ของ object ได้
    • แยก primitive กับ object และรู้กับดัก typeof null
    • เลือก === แทน == ได้อย่างมีเหตุผล
    • บอก falsy 6 ตัวได้ครบ และรู้ว่า [] กับ "0" เป็น truthy
    • เขียน template literal ให้ output ตรง spec ทุกช่องว่าง

    ก่อนจะเขียนเงื่อนไขหรือฟังก์ชันอะไรให้ซับซ้อน ต้องมั่นใจก่อนว่า "ค่า" ที่ถืออยู่ในมือคืออะไรกันแน่ หลายครั้งที่ตรรกะถูกทั้งหมด แต่ระบบยังให้ 0 คะแนน เพราะพลาดตรงพื้นฐานที่ดูเหมือนเรื่องเล็กที่สุดในบทนี้

    const ล็อก "ป้าย" ไม่ได้ล็อก "ของข้างใน"

    นึกภาพกล่องพัสดุที่มีป้ายชื่อติดไว้ — ป้ายคือชื่อตัวแปร ของข้างในคือค่าที่มันถืออยู่ let กับ const สร้างกล่องแบบเดียวกันทุกอย่าง ต่างกันแค่ "แปะป้ายแล้วห้ามย้ายป้ายอีก" กับ "ย้ายทีหลังได้"

    จุดที่งงกันบ่อยคือ const ล็อกแค่ว่า ป้ายต้องชี้กล่องใบเดิมเสมอ ไม่ได้ล็อกว่าของข้างในห้ามแก้ ถ้าของข้างในเป็นกล่องอีกใบ (object) เปิดฝาแล้วสลับของข้างในได้ตามสบาย สิ่งที่ทำไม่ได้มีแค่การเอาป้ายไปแปะกล่องใบใหม่ทั้งใบ

    หลักปฏิบัติคือ ใช้ const เป็นค่าเริ่มต้นเสมอ แล้วสลับไป let เฉพาะตอนที่รู้แน่ว่าต้องเปลี่ยนป้ายไปชี้ค่าอื่นทั้งก้อน เช่น ตัวนับในลูป

    const cart = { qty: 1 };
cart.qty = 2;      // ได้ — แก้ของข้างในกล่องเดิม
cart = { qty: 5 };  // TypeError — เปลี่ยนป้ายไปชี้กล่องใหม่ไม่ได้

    primitive คัดลอกค่า · object คัดลอกที่อยู่

    ข้อมูลแบ่งเป็นสองกลุ่มที่ทำงานคนละแบบ กลุ่มแรกคือ primitive — ตัวเลข ข้อความ boolean null undefined — ก็อปใส่ตัวแปรใหม่แล้วได้ค่าชิ้นใหม่แยกกันเด็ดขาด กลุ่มที่สองคือ object (รวม array และ function) — ก็อปแค่ "ที่อยู่" ไม่ได้ก็อปของข้างใน สองตัวแปรจึงชี้กล่องใบเดียวกัน แก้ทางหนึ่งอีกทางเห็นด้วยทันที

    จุดนี้สำคัญมากเวลาเขียนฟังก์ชันที่รับ array หรือ object เข้าไปแล้วแก้ property ข้างในตรง ๆ — ต้นฉบับข้างนอกจะเปลี่ยนตามไปด้วยเงียบ ๆ โดยไม่ได้ตั้งใจ

    let a = 100; let b = a; b = 250;
console.log(a);  // 100 — คนละก้อน

const c1 = { total: 100 }; const c2 = c1; c2.total = 500;
console.log(c1.total);  // 500 — ก้อนเดียวกัน

    truthy กับ falsy — ค่าที่ "ดูเหมือนว่าง" แต่ไม่ได้ว่างเสมอไป

    ทุกค่าเวลาโดนใส่ในเงื่อนไข if (ค่า) จะถูกแปลงเป็น true หรือ false เสมอ ค่าที่แปลงแล้วได้ false เรียกว่า falsy มีอยู่แค่ 6 ตัวเป๊ะ ๆ ทั้งภาษา: false · 0 · "" · null · undefined · NaN — นอกนั้นเป็น truthy หมด

    ตัวที่หลอกตาที่สุดคือ [] กับ {} — ดูว่างเปล่าพอ ๆ กับ "" แต่เป็น truthy เพราะกฎเช็คแค่ว่าเป็น object ไหม ไม่ได้เช็คว่าข้างในมีอะไร อยากรู้ว่า array ว่างไหมต้องเช็ค arr.length === 0 อีกตัวคือสตริง "0" ที่เป็น truthy ต่างจากตัวเลข 0 ที่เป็น falsy

    truthy หรือ falsy — กดแล้วดูว่าเข้า if ไหม

    เลือกค่าด้านบน

    typeof — เครื่องมือเช็คชนิดที่มีรูรั่วอยู่ 1 จุด

    พิมพ์ typeof ค่า แล้วได้สตริงบอกชนิดกลับมา ใช้งานตรงไปตรงมาเกือบทุกกรณี แต่มีจุดเดียวที่มันโกหก และเป็นกับดักที่ถูกหยิบมาถามบ่อยมาก: typeof null คืน "object" ไม่ใช่ "null" เป็นบั๊กเก่าแก่ที่แก้ไม่ได้แล้วเพราะจะทำให้เว็บเก่าพังจำนวนมาก

    undefined"undefined"

    จดไว้ตรงนี้เจอ typeof x === 'object' แล้วอย่าเพิ่งดีใจ ต้องเช็ค x !== null ต่ออีกชั้นเสมอ ไม่งั้นเผลอเอา null ไปอ่าน property ต่อจะพังทันที — และ array ต้องใช้ Array.isArray() แยกต่างหาก

    typeof — เครื่องมือเช็คชนิดที่มีรูรั่ว 1 จุด

    กดค่าแล้วดูว่า typeof ตอบอะไร

    == แปลงชนิดให้ก่อนเทียบ · === ไม่ยอมแปลง

    == จะพยายามแปลงชนิดให้ตรงกันก่อนเทียบ ส่วน === เทียบดิบ ๆ ชนิดต้องตรงกันด้วยถึงจะเท่ากัน ปัญหาของ == คือกฎการแปลงซับซ้อนและขัดสามัญสำนึก — 0 == "" ได้ true, null == undefined ได้ true, "1" == 1 ได้ true ทีละคู่ดูสมเหตุสมผล แต่พอปนกันในโค้ดจริงจะกลายเป็นบั๊กที่หาไม่เจอ

    คู่ที่หลอกตา=====
    0 กับ ""true ⚠false
    null กับ undefinedtrue ⚠false
    "1" กับ 1true ⚠false
    NaN กับ NaNfalse เสมอfalse เสมอ
    พลาดกันบ่อยคิดว่า ค่า === NaN เช็ค NaN ได้ — NaN ไม่เท่ากับตัวมันเองแม้แต่ด้วย === ต้องใช้ Number.isNaN(ค่า) เท่านั้น

    == กับ === ต่างกันยังไง — พิมพ์ค่าสองฝั่งแล้วเทียบ

    vs พิมพ์แบบ JS เช่น null, "1", [], 0

    template literal — และช่องว่างที่สำคัญเท่าตัวอักษร

    วิธีเก่าคือใช้ + ต่อทีละท่อน ต้องคอยใส่ช่องว่างเอง วิธีใหม่คือ template literal ใช้ backtick ครอบแล้ววางตัวแปรใน ${} ตรง ๆ อ่านง่ายกว่ามาก

    แต่ประเด็นที่สำคัญกว่าความอ่านง่ายคือ ระบบตรวจอัตโนมัติเทียบข้อความแบบตัวต่อตัวอักษร ไม่ได้ตัดสินว่าความหมายถูกไหม — "ราคารวม: 590 บาท" กับ "ราคารวม:590 บาท" หรือ "ราคารวม: 590บาท" ถือเป็นคนละสตริงกันทั้งสิ้น นี่คือเหตุผลที่เขียนโค้ดถูกตรรกะ 100% แต่ยังได้คะแนนไม่เต็ม เพราะพลาดที่ "การพิมพ์ผล" ไม่ใช่ "การคำนวณ"

    template literal — ต้องได้ เสื้อยืด x3 = 750 บาท เป๊ะ

    `${p.name} x${qty} = ${} บาท`

    พลาดกันบ่อย

    • เทียบด้วย == แล้วเจอบั๊กเงียบ — ใช้ === เป็นค่าเริ่มต้นเสมอ
    • เช็ค array ว่างด้วย if (arr) — array ว่างเป็น truthy ต้องดู .length
    • พิมพ์ output ผิดช่องว่างแล้วไปไล่แก้ตรรกะ — เทียบ spec ทีละตัวอักษรก่อน

    Checkpoint — สรุปสั้น ๆ

    • const ล็อกแค่ "ป้ายชื่อ" ไม่ได้ล็อก property ข้างในของ object
    • falsy มีแค่ 6 ตัวเป๊ะ ๆ — [] กับ {} เป็น truthy เสมอแม้จะว่างเปล่า
    • typeof null คืน "object" — เช็ค null ต้องใช้ === null เท่านั้น
    • ใช้ === เป็นค่าเริ่มต้น และตรวจ output ให้ตรง spec ถึงระดับช่องว่าง

    02 เงื่อนไข

    โปรแกรมเช็คจากบนลงล่าง เจอทางแรกที่จริงก็เข้าทันที — เรียงผิด เคสพิเศษหลุด

    บทที่ 02~18 นาทีเริ่มต้นออกสอบ

    จบบทนี้ต้องทำได้

    • อธิบายลำดับ if / else if / else ว่าเช็คทีละบรรทัดจากบนลงล่าง
    • ใช้ ternary แทน if/else สั้น ๆ และรู้ว่าต้องเก็บผลไว้
    • เรียงเงื่อนไข "แคบก่อนกว้าง"
    • รู้ว่า a <= x <= b ไม่ทำงาน ต้องใช้ &&
    • แยกวิธีเช็ค "ว่าง" — length === 0 · === "" · == null

    โปรแกรมเช็คเงื่อนไขจากบนลงล่างเสมอ เจอทางแรกที่จริงก็เดินเข้าทันที แล้วข้ามเงื่อนไขที่เหลือทั้งหมดไปเลย แม้เงื่อนไขข้างล่างจะเป็นจริงด้วยก็ตาม — ถ้าเรียงลำดับผิด เคสที่ควรถูกจับได้อาจหลุดเข้าไปในทางที่ผิดโดยไม่มีใครรู้

    เช็คแคบก่อนกว้าง

    นี่คือกับดักคลาสสิกที่สุดของบทนี้ เวลาตรวจสอบยอดสั่งซื้อมักมีทั้งเคส "ผิดปกติ" (ยอดติดลบ) ปนกับเคส "ปกติแต่แบ่งเป็นช่วง" ถ้าเช็คเงื่อนไขกว้างก่อน เคสผิดปกติจะหลุดเข้าไปโดนตัดสินว่าปกติไปเลย เพราะ if แรกที่ตรงจะจับตัวไปทำงานแล้ว

    // ผิดลำดับ — เช็คช่วงกว้างก่อนเคสผิดปกติที่แคบกว่า
if (amount < 1000) return 'ปกติ';
if (amount < 0)    return 'ยอดติดลบ';
// amount = -50 → เข้า if แรกทันที เพราะ -50 < 1000 เป็นจริง

    ทางแก้คือเรียงเงื่อนไขที่ แคบและเฉพาะเจาะจงที่สุดไว้บนสุด แล้วค่อยไล่ไปเงื่อนไขที่กว้างขึ้นด้านล่าง

    // ผิด — -50 เข้า if แรกไปเลย ไม่มีวันถึง throw
if (amount < 1000) return 'ปกติ';
if (amount < 0)    return 'ติดลบ';

// ถูก — เคสแคบไว้บน
if (amount < 0)    return 'ติดลบ';
if (amount < 1000) return 'ปกติ';

    ternary คือ expression — ต้องมีที่รับค่า

    ternary ไม่ใช่แค่ "if/else แบบย่อ" มันคือ expression ที่ประเมินแล้วได้ค่ากลับมาทันที เก็บใส่ตัวแปรได้เลยในบรรทัดเดียว ต่างจาก if/else ที่เป็นคำสั่ง ไม่ได้คืนค่าอะไรออกมาให้เก็บ

    กับดักที่เจอบ่อยคือเขียน ternary เป็นบรรทัดลอย ๆ โดยไม่เก็บผลไว้ที่ไหนเลย ผลที่ตัดสินใจได้ก็หายไปเฉย ๆ — มันไม่ได้พิมพ์อะไรออกมาเอง มันแค่ "คืนค่า" ถ้าไม่มีที่รับก็เหมือนไม่ได้ทำอะไรเลย และถ้าตรรกะเริ่มซับซ้อนเกิน 2 ทางเลือก ให้กลับไปใช้ if/else เพราะ ternary ซ้อนกันอ่านยากกว่าเสมอ

    const label = total >= 500 ? 'ส่งฟรี' : 'ค่าส่ง 50 บาท';
total >= 500 ? 'ส่งฟรี' : 'ค่าส่ง 50 บาท';  // ❌ คำนวณแล้วทิ้ง

    เลื่อนยอดใช้จ่าย — ดูว่าหยุดที่บรรทัดไหน

    บาท

    ทำไม a <= x <= b ถึง "จริงเกือบเสมอ"

    กับดักนี้มาจากนิสัยเดิมจากวิชาคณิตศาสตร์ — JavaScript ไม่มี syntax เปรียบเทียบต่อเนื่องแบบนั้น มันตีความเป็นสอง operation เรียงจากซ้ายไปขวา: ประเมิน 0 <= x ก่อนได้ boolean แล้วเอา boolean นั้นไปเทียบกับ 100 ต่อ — true <= 100 แปลง true เป็น 1 กลายเป็น 1 <= 100 ซึ่งจริงแทบทุกกรณี ไม่ว่า x จะเป็นเท่าไหร่

    วิธีเขียนที่ถูกคือแยกเป็นสอง condition เชื่อมด้วย &&: x >= 0 && x <= 100 — ต้องเขียน x ซ้ำสองรอบ ดูยาวกว่า แต่เป็นวิธีเดียวที่ทำงานถูกจริง

    ทำไม 0 <= x <= 100 จริงเกือบเสมอ

    เงื่อนไข "ว่าง" — สามแบบที่เช็คคนละเรื่องกัน

    คำว่า "ว่าง" ในโค้ดจริงมีอย่างน้อยสามความหมาย และคนมักเลือกวิธีเช็คผิดเพราะไม่ได้แยกให้ชัดว่ากำลังถามอะไร

    ต้องการเช็ควิธีเขียนใช้กับ
    ไม่มีสมาชิกในลิสต์เลยcartItems.length === 0array
    เป็นสตริงว่างเป๊ะquery === ""string
    ยังไม่มีค่าเลย (null หรือ undefined)user.phone == nullตัวแปรใด ๆ
    จดไว้ตรงนี้== null เป็นจุดเดียวที่ตั้งใจใช้ == เพราะมันครอบทั้ง null และ undefined ในเงื่อนไขเดียว — ถ้าใช้ === null จะไม่ครอบ undefined ด้วย

    early return — เจอเงื่อนไขไม่ผ่านก็ออกทันที

    พอเจอเงื่อนไขที่ทำให้ฟังก์ชันทำงานต่อไม่ได้ ให้ return ออกทันที แทนที่จะซ้อน if ลึกเข้าไปเรื่อย ๆ วิธีนี้ยังช่วยลดโอกาสลืมเขียน branch ปิดท้ายด้วย เพราะแต่ละเงื่อนไขจบตัวเองทันทีที่บรรทัดนั้น เห็นทุกเส้นทางชัดกว่า

    พลาดกันบ่อย

    • เรียง guard กว้างก่อนแคบ — เคสพิเศษหลุด
    • เขียน a <= x <= b — ต้องแยกด้วย &&
    • ใช้ if (str) เช็คสตริงว่าง — "0" กับช่องว่างล้วนเป็น truthy

    Checkpoint — สรุปสั้น ๆ

    • เรียงเงื่อนไขที่แคบและเฉพาะเจาะจงไว้บนสุดเสมอ ไม่งั้นเคสพิเศษจะหลุดเข้าไปในทางที่กว้างกว่า
    • a <= x <= b ไม่ทำงานแบบคณิตศาสตร์ — ต้องแยกเขียนด้วย && เสมอ

    ฟังก์ชันรับของเข้ามาทางหนึ่ง แล้วต้องส่งคำตอบออกไปให้ถูกทาง — ผิดทางไปนิดเดียว งานที่คำนวณถูกทุกตัวอักษรก็กลายเป็นศูนย์คะแนนได้เงียบ ๆ
    return vs console.log
    นึกภาพเครื่องคิดเงินหน้าร้าน มันทำงานได้สองแบบ — แบบแรกคือคำนวณเสร็จแล้ว "แปะตัวเลขไว้บนจอหลังร้าน" ให้พนักงานเห็นเฉย ๆ นั่นคือ console.log แบบที่สองคือ "ส่งใบสรุปยอดออกมาทางช่องรับ" ให้ระบบหน้าบ้านหยิบไปใช้ต่อได้จริง นั่นคือ return — หน้าเว็บที่รอรับยอดไม่เคยแอบมองจอหลังร้านเลยสักครั้ง
    ฟังก์ชันที่ไม่มี return เลยสักบรรทัดจะให้ผลลัพธ์เป็น undefined เสมอ ไม่ว่าโค้ดข้างในจะคำนวณถูกแค่ไหน และถ้ามีหลายเส้นทาง (if/else) แล้วลืมปิดท้ายบางเส้นทางด้วย return เส้นทางที่ตกหล่นก็คืน undefined แบบเงียบ ๆ เหมือนกัน

    พารามิเตอร์ คือชื่อช่องรับที่ตั้งไว้ตอนนิยาม ส่วน อาร์กิวเมนต์ คือค่าจริงที่ส่งเข้าไปตอนเรียกใช้ ถ้าส่งไม่ครบ ช่องที่ไม่มีของมาเติมจะกลายเป็น undefined โดยอัตโนมัติ ไม่ error ไม่เตือนอะไรทั้งสิ้น
    ตั้งค่าเริ่มต้นได้ด้วย = ค่าตั้งต้น ต่อท้ายชื่อพารามิเตอร์ แต่จุดที่ต้องจำให้แม่นคือ default ทำงานเฉพาะตอนที่พารามิเตอร์นั้นได้ค่า undefined เท่านั้น — ถ้าตั้งใจส่ง null, "" หรือ 0 เข้าไปเอง JavaScript ถือว่า "มีของส่งมาแล้ว" และจะไม่แตะ default เลย ต่อให้ค่านั้นจะดูว่างเปล่าในสายตาคนก็ตาม

    callback — ใส่วงเล็บหรือไม่ใส่

    • มี if ครบทุกเคสแต่ไม่มี return ปิดท้าย — เดินตกขอบได้ undefined
    • ส่ง callback แบบ filter(fn()) — วงเล็บคือเรียกทันที

    ก่อนเรียก method ไหนกับ array ต้องถามตัวเองก่อนเสมอว่า — มันจะแก้ของเดิม หรือส่งของใหม่กลับมาให้
    สองนิสัยของ array method
    ลองถามว่า "ถ้าเรียก method นี้แล้วไม่เก็บผลไว้ที่ไหนเลย ข้อมูลต้นฉบับจะเปลี่ยนไหม" — ถ้าเปลี่ยน แปลว่ามันแก้ต้นฉบับ (mutating) เรียกลอย ๆ ก็มีผลอยู่ดี ถ้าไม่เปลี่ยน แปลว่ามันคืนของใหม่ (non-mutating) เรียกลอย ๆ แล้วไม่เก็บผล ค่าที่คำนวณเสร็จจะหายไปเฉย ๆ เหมือนไม่เคยเรียกเลย
    เรื่องนี้สับสนง่ายเพราะทั้งสองกลุ่มเรียกด้วยหน้าตาเหมือนกันเป๊ะ ไวยากรณ์ไม่บอกอะไรเลย ต้องจำเป็นรายตัวเท่านั้น
    methodหมวดคืนอะไรต้นฉบับเปลี่ยน?
    push / popแก้ต้นฉบับความยาวใหม่ / สมาชิกที่ดึงออกเปลี่ยน
    shift / unshiftแก้ต้นฉบับสมาชิกแรก / ความยาวใหม่เปลี่ยน
    spliceแก้ต้นฉบับarray ของสมาชิกที่ถูกลบเปลี่ยน
    sort / reverseแก้ต้นฉบับarray เดิม (จัดเรียงแล้ว)เปลี่ยน ⚠
    slice / concatคืนของใหม่array ใหม่ไม่เปลี่ยน
    mapคืนของใหม่array ใหม่ ยาวเท่าเดิมไม่เปลี่ยน
    filterคืนของใหม่array ใหม่ เฉพาะตัวที่ผ่านไม่เปลี่ยน
    findคืนของใหม่สมาชิกตัวแรกที่ผ่าน หรือ undefinedไม่เปลี่ยน
    some / everyคืนของใหม่true / falseไม่เปลี่ยน
    joinคืนของใหม่stringไม่เปลี่ยน
    MUTATING VS NON-MUTATINGmethod ที่แก้ต้นฉบับเข้าไปเปลี่ยนสมาชิกใน array เดิมตรง ๆ ไม่ต้องเก็บผลก็มีผลอยู่ดี ส่วน method ที่คืนของใหม่ไม่แตะต้นฉบับเลย ต้องเก็บสิ่งที่มันคืนมาใส่ตัวแปรหรือ return ต่อ ไม่งั้นผลลัพธ์จะหายไปเฉย ๆ
    map vs filter vs find — คืนอะไรกลับมาไม่เหมือนกัน
    ทั้งสามรับ callback หน้าตาคล้ายกันมากจนสับสนได้ง่าย แต่คืนของกลับมาคนละแบบ — map คืน array ใหม่ที่ ยาวเท่าต้นฉบับเป๊ะ เพราะแปลงค่าทุกตัวโดยไม่ตัดตัวไหนทิ้ง, filter คืน array ใหม่ที่ อาจสั้นกว่าเดิม เพราะคัดเก็บเฉพาะตัวที่ผ่านเงื่อนไข, find คืน สมาชิกตัวเดียว คือตัวแรกที่ผ่าน หรือ undefined ถ้าไม่มีตัวไหนผ่านเลย
    

    กด method แล้วดูว่าต้นฉบับเปลี่ยนไหม (เริ่มจากชุดเดิมทุกครั้ง)

    reduce: ตั้งถัง → วนทีละชิ้น → หย่อนของลงถัง → คืนถัง
    reduce ทำงานเป็น 4 จังหวะเสมอ — ตั้งถัง กำหนด initial value ให้ accumulator, วนทีละชิ้น ไล่ทีละสมาชิก, หย่อนของลงถัง เอาผลจากสมาชิกตัวนั้นรวมเข้ากับสิ่งที่อยู่ในถังแล้ว, และ คืนถัง เมื่อวนครบ
    ต่างจาก map/filter/find ที่ทำงานทีละตัวแล้วจบในตัวมันเอง — reduce สะสมผลจากตัวก่อนหน้าเข้าไปเรื่อย ๆ นี่คือความต่างที่ทำให้มันทรงพลังกว่า
    ต้องมี initial value เสมอ (ค่าตัวที่สองท้าย callback) ถ้าไม่ใส่ JavaScript จะหยิบสมาชิกตัวแรกมาเป็นถังตั้งต้นแทน ซึ่งเสี่ยงมากถ้า array ว่างเปล่า — จะ error ทันที
    reduce จัดกลุ่มข้อมูล
    const grouped = products.reduce((groups, product) => {
  groups[product.category] = groups[product.category] || [];
  groups[product.category].push(product.name);
  return groups;
}, {});
    บรรทัด || [] สำคัญมาก — รอบแรกที่เจอหมวดหมู่ใหม่ ถังยังไม่มีช่องเก็บของหมวดนั้น ค่าจึงเป็น undefined ถ้าเผลอเรียก .push() ใส่ undefined ตรง ๆ จะพังทันที
    พลาดกันบ่อยpush เข้า groups[key] ก่อนสร้าง array ให้มันก่อน — ถ้า error บอกว่า "Cannot read properties of undefined (reading 'push')" ให้สงสัยจุดนี้ไว้ก่อนเลย
    

    เดิน reduce ทีละก้าว — ดูถัง (acc) สะสม
    

    

    


    sort เรียงยังไงถ้าไม่บอกวิธีเปรียบเทียบ
    sort() ถ้าไม่ใส่ comparator จะ แปลงสมาชิกทุกตัวเป็น string ก่อนเทียบเสมอ — สำหรับตัวอักษรแทบไม่มีปัญหา แต่สำหรับตัวเลขนี่คือกับดักคลาสสิก เพราะการเทียบแบบ string เทียบทีละตัวอักษรจากซ้ายไปขวา ไม่ได้สนใจว่าตัวเลขทั้งก้อนมีค่าเท่าไหร่
    console.log([40, 5, 100].sort());
// [100, 40, 5] — เรียงแบบ string: "1" มาก่อน "4" มาก่อน "5"
    ใส่ (a, b) => a - b เพื่อเรียงน้อยไปมาก หรือ (a, b) => b - a เพื่อเรียงมากไปน้อย — กติกาคือคืนค่าติดลบ a มาก่อน b, คืนค่าบวก b มาก่อน a
    

    sort ตัวเลข — มี comparator หรือไม่มี
    

    

    


    

    

    พลาดกันบ่อย

    • ลืม initial value ให้ reduce
    • groups[key].push(...) ก่อนสร้าง array — ต้อง groups[key] = groups[key] || []
    

    

    


    Checkpoint — สรุปสั้น ๆ
    • ก่อนเรียก method ไหนกับ array ให้เช็คก่อนว่ามันแก้ต้นฉบับหรือคืนของใหม่

    • reduce ต้องมี initial value เสมอ และต้องเช็ค groups[key] || [] ก่อน push ตอนจัดกลุ่ม
    • sort() ที่ไม่ใส่ comparator เรียงแบบ string เสมอ — ใส่ (a,b) => a - b เพื่อเรียงเป็นตัวเลขจริง

    = ไม่ใช่การคัดลอก — สองตัวแปรอาจชี้ก้อนเดียวกัน
    เขียน const userB = userA ไม่ได้สร้างก้อนข้อมูลใหม่เลยสักนิด มันแค่บอกว่า "userB ก็ชี้ไปที่ก้อนเดียวกับ userA" แก้ property ผ่าน userB จึงกระทบ userA ไปด้วย เพราะทั้งคู่ชี้ก้อนเดียวกันจริง ๆ ไม่ใช่คนละก้อนที่หน้าตาเหมือนกัน
    === ของ object เทียบว่า ชี้ไปก้อนเดียวกันหรือเปล่า ไม่ได้เทียบว่าค่าข้างในเหมือนกันไหม — สองก้อนที่มีทุก property เหมือนกันเป๊ะแต่คนละก้อน เทียบด้วย === จะได้ false เสมอ

    วน object ได้ 3 วิธี — ผลเหมือนกัน หน้าตาต่างกัน
    Object.keys(obj) ได้ array ของชื่อ key ทั้งหมด, Object.values(obj) ได้ค่าทั้งหมด, Object.entries(obj) ได้คู่ [key, value] — เอาไปวนต่อกับ forEach หรือ for...of ได้ทันที นอกจากนี้ยังมี for...in ที่วน key ได้ตรง ๆ โดยไม่ต้องผ่าน Object.keys() ก่อน

    จุด กับ วงเล็บเหลี่ยม — สองทางเข้าถึง property
    dot notation เขียนชื่อ key ตรง ๆ ต่อท้ายจุด ใช้เมื่อรู้ชื่อ key แน่นอนตอนเขียนโค้ด bracket notation เขียนชื่อ key เป็นสตริงในวงเล็บเหลี่ยม ใช้ได้ทั้งตอนรู้ชื่อตรง ๆ และตอนชื่อ key มาจากตัวแปร
    กับดักที่พลาดบ่อยคือ userProfile.key ไม่ได้แปลว่า "หยิบชื่อ key จากตัวแปร key" แบบที่ userProfile[key] ทำ — มันแปลว่า "หา property ที่ชื่อว่า key ตรงตัวอักษร" ซึ่งมักไม่มีอยู่จริง ผลจึงเป็น undefined และถ้าเขียน userProfile[name] โดยลืม quote JavaScript จะไปหาตัวแปรชื่อ name มาใช้แทน ถ้าไม่มีก็ error ทันที
    สะกด key ผิดแล้ว JS เงียบ ไม่เตือนอะไรเลย
    JavaScript ไม่เช็คให้ว่า key ที่พิมพ์ตรงกับที่นิยามไว้จริงไหม — เขียนผิดแค่ตัวเดียวก็กลายเป็น key ใหม่ ทันที ไม่มี error ไม่มีคำเตือน เพราะในสายตา JavaScript มันแค่กำลังสร้าง property ใหม่ตามปกติ อาการที่เจอคือแก้ค่าไปแล้วแต่ค่ายังเหมือนเดิมทุกครั้ง
    จดไว้ตรงนี้สงสัยว่าทำไมแก้ property แล้วค่าไม่เปลี่ยนสักที ลอง console.log(Object.keys(obj)) ดูก่อนได้เลย — ถ้าเห็นชื่อ key แปลก ๆ โผล่มาเพิ่มที่ไม่เคยตั้งใจสร้าง แปลว่าพิมพ์ชื่อ key ผิดที่ไหนสักจุดแน่นอน

    • สะกด key ผิดตอนแก้ — ได้ key ใหม่เงียบ ๆ ค่าเดิมไม่เปลี่ยน

    • dot ใช้ตอนรู้ชื่อ key แน่นอน · bracket ใช้ตอน key มาจากตัวแปร — เขียนชื่อตรง ๆ ใน bracket ต้องมี quote
    • ตัวแปรที่เก็บ object ชี้ไปหาก้อนข้อมูล ไม่ได้ถือไว้เอง — const b = a ไม่ได้สำเนาใหม่ให้
    • === ของ object เทียบว่าชี้ก้อนเดียวกันไหม ไม่ได้เทียบค่าข้างใน
    • สะกด key ผิดไม่มี error เตือนเลย — JS สร้าง key ใหม่ให้เงียบ ๆ

    Date คือจำนวน millisecond เท่านั้นเอง
    ข้างใน Date ทุกก้อนคือจำนวน millisecond ที่นับตั้งแต่เที่ยงคืนของวันที่ 1 มกราคม ค.ศ. 1970 (จุดอ้างอิงนี้เรียกว่า epoch) วันที่ในอนาคตคือเลขที่มากกว่า อดีตคือเลขที่น้อยกว่า — ทุกครั้งที่เทียบวันที่สองวัน จริง ๆ แล้วคือการเทียบตัวเลขสองตัวเฉย ๆ
    EPOCH TIMEจุดเริ่มนับเวลาของคอมพิวเตอร์เกือบทุกระบบคือ 00:00:00 UTC วันที่ 1 มกราคม 1970 — Date เก็บระยะห่างจากจุดนั้นเป็น millisecond (ไม่ใช่วินาที) ตัวเลขนี้เรียกว่า timestamp เอาไปบวกลบเปรียบเทียบกันได้เหมือนตัวเลขทั่วไป
    ดึงส่วนประกอบออกจาก Date
    ตัวที่สับสนกันบ่อยที่สุดคือ getDate() กับ getDay() ชื่อคล้ายกันมากแต่คืนคนละอย่าง

    หาผลต่างระหว่างวัน — สูตรที่พลาดกันบ่อยที่สุด
    เพราะ Date คือตัวเลข การลบ Date สองตัวจึงได้ผลต่างเป็นจำนวน millisecond ตรง ๆ ทิศทางคือ ใหม่ลบเก่า ถ้าอยากได้ผลบวก

    Date สองตัวเทียบกันด้วย > หรือ < ได้เลย แต่ === ใช้ไม่ได้ เพราะ Date เป็น object — สอง Date ที่แทนเวลาเดียวกันเป๊ะแต่คนละก้อนจะได้ false เสมอ ต้องเทียบด้วย .getTime() ทั้งสองฝั่งแทน

    ข้อมูลจากผู้ใช้ไม่เคยสวยเป๊ะเหมือนตัวอย่างในห้องเรียน — try/catch คือด่านสุดท้ายที่กันไม่ให้ความผิดพลาดเล็ก ๆ ลากทั้งไฟล์ล้มตามไปด้วย
    ถ้าข้อมูลที่ส่งมาเสียรูป JSON.parse จะไม่ได้แค่คืน undefined เงียบ ๆ เหมือนหลายจุดในบทก่อน ๆ — มันหยุดทั้งไฟล์ทันที ทุกบรรทัดหลังจากนั้นไม่ทำงานเลย ทั้งหน้าเว็บอาจค้างโดยที่ผู้ใช้ไม่รู้ว่าเกิดอะไรขึ้น
    โครงเปล่าที่ต้องเขียนได้หลับตา
    ก่อนคิดโค้ดข้างใน ต้องเขียนโครงเปล่า ๆ ให้คล่องก่อน เพราะถ้าคิดโค้ดพร้อมกังวลเรื่องปีกกาไปด้วย มักพลาดทั้งคู่ ที่เขียนไม่ได้จริงคือ try ไม่มีปีกกา, catch เดี่ยว ๆ ไม่มี try นำหน้า — ยกเว้นแบบเดียวที่เขียนได้โดยไม่มี catch คือ try...finally
    ลำดับสำคัญมาก — ถ้าเกิด error ขึ้นระหว่างบรรทัดไหนใน try โปรแกรมจะกระโดดเข้า catch ทันที บรรทัดที่เหลือใน try จะไม่ทำงานเลย จากนั้นไม่ว่าทางไหนก็วิ่งไปจบที่ finally เสมอ
    จดไว้ตรงนี้ผลจาก try ต้องรับมาใช้ด้วย — JSON.parse ไม่ได้แก้ string เดิม แต่คืน object ใหม่ออกมา ต้องเก็บผลที่ parse ได้ไว้ในตัวแปรใหม่แล้วใช้ตัวนั้นแทน · และตัวแปรที่จะ reassign ใน finally ต้องประกาศด้วย let ตั้งแต่แรก

    ผ่านบางเทสหลอกได้
    ระบบตรวจมักรันหลายเทสต่อ 1 ข้อ แล้วรายงานว่าผ่านกี่จากทั้งหมดกี่เทส — จุดที่ต้องระวังคือ ผ่าน 2 จาก 3 ไม่ได้แปลว่า "เกือบถูกแล้ว" เทสที่ผ่านอาจผ่านเพราะข้อมูลของเคสนั้นบังเอิญไม่โดนจุดที่โค้ดเราพัง หรือผ่านแบบ "บังเอิญ" เช่นคำนวณผิดสูตรแต่ได้ผลตรงกับเคสนั้นพอดี
    วิธีที่ปลอดภัยกว่าคือ มองเทสที่ยังไม่ผ่านเป็นเบาะแส ไม่ใช่ตัวชี้วัดว่าใกล้เสร็จแค่ไหน — ดูว่าเคสที่ไม่ผ่านมีอะไรพิเศษ (ค่าติดลบ, ว่าง, ซ้ำ, ยาวผิดปกติ) ต่างจากเคสที่ผ่านตรงไหน มันมักชี้ตรงไปที่ edge case ที่โค้ดยังไม่ครอบคลุม

    เช็ค 3 จุดก่อนกดส่ง

    #เช็คอะไร
    ①มี return หรือยัง — ฟังก์ชันที่เขียนจบแล้วมีบรรทัด return อยู่จริงไหม หรือลืมไว้แค่ console.log
    ②ข้อความตรง spec เป๊ะทุกช่องว่างไหม — ระบบตรวจเทียบ string แบบตรงตัวอักษร ช่องว่างเกินหรือขาดแม้ตัวเดียวก็ไม่ผ่าน
    ③ชื่อตัวแปร/property สะกดตรงไหม — เทียบชื่อ key ทีละตัวอักษร โดยเฉพาะตัวพิมพ์เล็ก-ใหญ่
    เช็คลิสต์นี้เรียงจากปัญหาที่รุนแรงที่สุดไปหาละเอียดที่สุดโดยตั้งใจ — ① เช็คก่อนว่าฟังก์ชันมีทางส่งค่ากลับหรือยัง เพราะถ้าไม่มี ต่อให้ ② กับ ③ ถูกหมดก็ยังได้ undefined อยู่ดี
    เทคนิคตามหาต้นเหตุ
    เมื่อ 3 จุดข้างบนเช็คแล้วยังไม่พบ ให้ใช้ 2 เทคนิคนี้ต่อ ทั้งคู่ไม่ต้องใช้เครื่องมือพิเศษอะไรเลย — แทรก console.log ทีละจุด วางไว้ระหว่างทางที่ข้อมูลไหลผ่าน แล้วดูว่าค่าเริ่มผิดตั้งแต่จุดไหน · comment ครึ่งไฟล์ออก ถ้า error บอกตำแหน่งไม่ชัด ลอง comment โค้ดครึ่งท้ายออกชั่วคราวแล้วรันดูว่า error ยังอยู่ไหม ถ้าหายไปแปลว่าต้นเหตุอยู่ในครึ่งที่ comment ออก แล้วแบ่งครึ่งของครึ่งนั้นต่อไปเรื่อย ๆ จนเจอบรรทัดที่แท้จริง

    13 DOM: เอกสารที่กลายเป็นต้นไม้
    

    HTML เป็นข้อความที่มีลำดับชั้น พอวาดเป็นแผนภาพจะได้ต้นไม้ 1 ต้น — ต้นไม้ต้นนั้นแหละคือ DOM

    • แยก root node กับ root element ได้ และบอกได้ว่าทำไมต้องมีทั้งสองอย่าง

    HTML ที่เราเขียนเป็นเอกสาร text-based ที่มีลำดับชั้น เมื่อ browser โหลดมันเข้ามา จะไม่ได้เก็บไว้เป็นข้อความเฉย ๆ แต่แปลงเป็นโครงสร้างต้นไม้ในหน่วยความจำ แล้วเปิดทางให้โปรแกรมเข้าไปเปลี่ยน structure, style และ content ของหน้าได้ — นั่นคือ DOM (Document Object Model)
    


    สองอย่างที่ต้องแยกให้ออกตั้งแต่ต้น: DOM ไม่ใช่ภาษาโปรแกรม และ DOM ไม่ใช่ของ JavaScript ทุกภาษามี library จัดการ DOM ของตัวเอง และ DOM ไม่ได้ใช้กับแค่ HTML — เอกสารใด ๆ ที่มีลำดับชั้นอย่าง XML ก็จำลองด้วยแนวคิดเดียวกันได้ แต่ถ้าไม่มี DOM ภาษา JavaScript ก็จะไม่มีความเข้าใจใด ๆ เกี่ยวกับหน้าเว็บเลย
    


    ทำไมต้องจำลองเป็นต้นไม้ในหน่วยความจำ — ให้คิดถึง แผนที่ ถ้าไม่รู้ว่า node ไหนอยู่จุดไหน เราก็อ้างถึงจุดที่จะเพิ่ม ลบ หรือแก้ไขไม่ได้ สิ่งที่ต้องเรียนจึงมี 2 อย่างคู่กันเสมอ: แนวคิดของการจำลองต้นไม้ และ คำสั่ง JavaScript ที่ใช้จัดการต้นไม้นั้น
    


    DOM (DOCUMENT OBJECT MODEL)การจำลองเอกสารเป็นต้นไม้ของ node เพื่อให้โปรแกรมเข้าไปแก้ไขได้ — เป็น cross-platform และ language-independent
HTML ที่โหลดมาครั้งแรก อาจไม่ใช่ HTML สุดท้าย เมื่อผู้ใช้มีปฏิสัมพันธ์ node ต่าง ๆ จะเปลี่ยนตามไป นั่นคือ dynamic page ที่เกิดจาก DOM + Event

    DocumentFragment — แตะ DOM จริงให้น้อยที่สุด
    

    ทุกครั้งที่เพิ่ม element เข้า DOM จริง browser ต้องคำนวณ layout ใหม่ (reflow) และวาดใหม่ (repaint) — วนลูปเพิ่ม 1,000 ตัวก็เกิด 1,000 ครั้ง
    

    DocumentFragment คือ พื้นที่พักชั่วคราวในหน่วยความจำ ที่ไม่ได้เป็นส่วนหนึ่งของหน้าเว็บจริง สร้างทุกอย่างลงใน fragment ก่อน แล้วค่อย appendChild เข้า DOM จริง ครั้งเดียว — ผลลัพธ์เหมือนกันเป๊ะ แต่ reflow/repaint เกิดครั้งเดียว
    


    const fragment = document.createDocumentFragment();
const list = document.getElementById('list');

for (let i = 0; i < 1000; i++) {
    const li = document.createElement('li');
    li.textContent = 'Item ' + i;
    fragment.appendChild(li);   // ยังไม่แตะ DOM จริง
}
list.appendChild(fragment);     // แตะ DOM จริงครั้งเดียว
